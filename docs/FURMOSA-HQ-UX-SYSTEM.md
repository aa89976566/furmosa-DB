# Furmosa HQ 後台設計規則

> 狀態：v0.1 討論底稿
>
> 適用：Furmosa HQ 總部後台與合作店家 POS 相關工作
>
> 目的：讓 ChatGPT、Codex、Cursor、Claude 與人員使用同一套設計判斷

## 1. 後台要解決的問題

Furmosa HQ 不是資料展示網站，而是讓總部與店員把今天的工作做完。

- 總部：看全局、處理例外、開通合作、補貨、對帳、處理會員問題。
- 店員：完成今天的換罐、銷售或核銷，不閱讀總部內部資料。
- 毛爸媽：只看與自己下一步有關的價格、資格、門市與進度。

## 2. 八條共同準則

1. 一個畫面只處理一件主要任務。
2. 新增前先搜尋，找到既有資料就開功能，不重建。
3. 一間實際門市只有一個店家編號，合作功能可以多選。
4. 主畫面只顯示現在能做什麼；一次性資訊放進詳細資料。
5. 不能操作時，說明原因並提供下一步。
6. 價格、資格與狀態由系統規則決定，畫面不得讓人自行猜。
7. HQ 與 POS 登入及工作畫面分開，但共用同一筆店家與交易紀錄。
8. 一次只完成一條完整工作圈，驗收後再進下一圈。

## 3. 任務型畫面

新增訂單、建立店家、開通合作等多步工作，統一使用任務精靈。

1. 顯示目前步驟，例如「第 1 步，共 4 步」。
2. 每一步只問一個決定，畫面只保留一個主要按鈕。
3. 優先使用大按鈕、選擇卡與搜尋結果，不堆疊長表單。
4. 下一步尚不可執行時，按鈕直接停用並說明缺少什麼。
5. 完成後顯示清楚成果與下一個可選任務。
6. 返回上一步不得清掉已填內容。

### 任務精靈的共同骨架

| 區域 | 必須回答 |
|---|---|
| 頁首 | 我現在在做什麼？進行到哪一步？ |
| 主區 | 這一步只要決定什麼？ |
| 說明 | 為什麼不能做？下一步是什麼？ |
| 頁尾 | 上一步、唯一主要動作 |
| 完成頁 | 剛完成什麼？資料會影響哪裡？ |

## 4. 新增／開通合作店的固定流程

### 第一步：先找店家

可搜尋店名、電話、店家編號與舊核銷連結。

- 找到既有門市：選取該店，進入「開通合作功能」。
- 找到相似或待確認資料：停止新增，交由總部確認。
- 確認找不到：才顯示「建立新門市」。

### 第二步：選合作功能

使用三張可多選的大卡片：

- 換罐計畫
- 美容折抵／核銷
- 寄賣合作

從換罐頁進入時，只預選「換罐計畫」，不得自動開通寄賣。

### 第三步：填必要資料

只顯示建立門市及所選功能真正需要的欄位。非必要資料延後補齊。

### 第四步：確認

清楚列出門市、合作功能、登入需求及尚未完成事項，再建立或開通。

### 完成

用一句話說明「這家店已準備好什麼」，再提供建立店員帳號等下一個任務。

## 5. 資訊層級

### 主畫面保留

- 今天待處理的工作
- 是否可以操作
- 阻擋原因
- 下一步
- 需要比較的少量核心數字

### 移到詳細資料

- 地址完整格式與公司資料
- 申請過程與確認歷史
- 舊連結、內部編號與技術原因
- 長篇活動說明
- 不影響今天操作的統計

### 不放在正式主畫面

- 測試／示範資料
- 重複的店家卡與交易卡
- 沒有下一步的彩色狀態
- 只給工程人員看的資料名稱
- 一次性成功訊息與教學說明

## 6. 視覺與互動

- 先建立清楚層級，再使用品牌色；顏色不負責代替文字。
- 同一頁最多一個主要實心按鈕。
- 狀態色只保留：可做、注意、阻擋、完成。
- 桌機可使用表格；手機改為同資訊順序的卡片，不橫向硬塞表格。
- 主要文字與按鈕需讓忙碌中的店員一眼讀懂。
- 危險操作必須說明影響，並要求原因或再次確認。
- 停用按鈕旁必須有人話原因，不能只變灰。

## 7. 遊戲感的使用邊界

採用 Duolingo 式的「被引導與有進度」，不做幼稚化裝飾。

### 可以使用

- 清楚步驟與完成進度
- 每完成一步立即回饋
- 大型選項卡與明確主按鈕
- 完成任務後的簡短成就感
- 今日任務逐項完成

### 不使用

- 為了熱鬧而增加徽章、彩帶或大量顏色
- 把金流、核銷或資料衝突做成遊戲
- 讓動畫妨礙操作速度
- 以排名刺激店員處理高風險任務

## 8. 新畫面驗收清單

- 使用者能否在 5 秒內說出這頁要做什麼？
- 是否只有一個主要任務與主要按鈕？
- 是否先找既有資料，再允許新增？
- 不能操作時，是否同時顯示原因與下一步？
- 手機與桌機是否維持相同資訊順序？
- 是否移除了重複、一次性與工程用資訊？
- 是否沒有混用 HQ 與 POS 工作？
- 是否可安全返回、取消或恢復？

## 9. 多 AI 協作規則

ChatGPT、Codex、Cursor、Claude 開工前都必須先讀本文件、統一用詞與目前進度。

- GitHub 文件是共同依據，聊天內容不是正式規則。
- Claude 可作第二位設計審查者，負責找矛盾、過度複雜與語意問題。
- 任何 AI 的建議都先列為提案，經總部確認後才能改成鎖定規則。
- 同一工作圈只指定一個執行者，避免兩邊同時修改相同檔案。
- 發現文件與現況不一致時先停下回報，不自行選一個版本。
