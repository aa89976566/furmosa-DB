## 2. 不可違反的帳務原則

1. **補貨不是營收。** 商品送到店家只改寄賣庫存，不產生銷售或佣金。
2. **實際售出才認列。** 店家 POS 完成銷售後才產生銷售額、店家佣金及 Furmosa 應收。
3. **換罐交付不是寄賣銷售。** 不得套用一般寄賣 20%／30% 佣金。
4. **交易發生時凍結規則。** 售價、佣金率、佣金金額、收款方向、獎勵面額與規則版本必須 snapshot。
5. **歷史不可重算。** 後台修改規則只影響新交易，不得改寫既有銷售、券、結算或付款。
6. **不可刪除已完成財務事實。** 錯誤只能新增 reversal／adjustment。
7. **金額由伺服器計算。** 不相信瀏覽器傳入的佣金、店家、規則版本、應收或應付。
8. **同一來源只能結算一次。** 所有銷售、券補貼、代收款與調整都必須有 canonical source key。
9. **結算與付款分離。** `approved` 只代表金額核准；有實際付款流水才可宣稱已收款或已撥款。
10. **未知資料 fail closed。** 找不到規則、來源互相衝突或資料不完整時，不自行猜測、不自動入帳。

## 3. 寄賣佣金規則

### 3.1 基準規則

| 商品類型 | 店家佣金基準 |
|---|---:|
| 肉乾／一般零食 | 20% |
| 凍乾 | 30% |
| 換罐計畫商品 | 不適用一般寄賣佣金 |

### 3.2 HQ 個別設定

HQ 可按「店家 × 商品」設定佣金。解析順序固定為：

1. 有效的店家商品個別規則。
2. 商品類型基準：凍乾 30%、肉乾／一般零食 20%。
3. 若商品無法可靠分類，不得猜 20% 或 30%，交易應被擋下並交由 HQ 補規則。

允許的設定方式：

- `percent`：以實際成交額乘百分比。
- `amount`：每件固定佣金；若啟用，必須在交易 line 保存單件佣金及總佣金。

後台變更必須保存操作人、時間、舊值、新值與生效時間。不得只覆蓋而沒有稽核紀錄。

### 3.3 銷售認列

每張完成銷售的每一個商品 line 必須保存：

- 店家與商品 ID。
- 實際成交單價、數量與成交總額。
- 佣金模式、率／固定額、佣金總額。
- Furmosa 應收金額。
- 收款通道。
- 規則版本及規則來源。
- 發生時間與不可重複的來源鍵。

店家現場收款時：

```text
店家應付 Furmosa = 實際成交總額 − 店家佣金
```

Furmosa 透過 LINE／綠界代收時：

```text
Furmosa 應付店家 = 店家佣金
```

### 3.4 範例

店家售出 300 元肉乾，佣金 20%：

| 項目 | 金額 |
|---|---:|
| 店家收取消費者款項 | 300 |
| 店家佣金 | 60 |
| 店家應付 Furmosa | 240 |

店家售出 300 元凍乾，佣金 30%：

| 項目 | 金額 |
|---|---:|
| 店家收取消費者款項 | 300 |
| 店家佣金 | 90 |
| 店家應付 Furmosa | 210 |

### 3.5 退款

- 原銷售與原佣金 snapshot 永不修改。
- 退款建立新的反向財務紀錄。
- 佣金依原交易的佣金 snapshot 回沖，不使用目前後台的新規則。
- 已進入核准／已付款結算的差額，進下一期 adjustment，不重開原結算。
- 庫存是否回補依商品是否實際退回且仍可銷售決定，不能因財務退款就自動增加庫存。

## 4. 換罐計畫帳務規則

### 4.1 收款與一般分潤分離

- 首罐／換罐費由 Furmosa 線上收款；店家不得自行標記付款成功。
- 換罐交付不建立一般寄賣 sale，不套 20%／30%。
- 換罐庫存流水必須可與一般寄賣進貨、銷售分辨。

### 4.2 點數

- 點數按店家分開累積，跨店不可合併。
- 合格換罐完成且顧客完成必要的新罐登錄後才加點。
- 每滿 10 點可以兌換一次同店使用的未來抵用權益。
- 兌換時扣除 10 點；點數與兌換都必須有不可變 ledger。

### 4.3 200／250 元規則

HQ 後台可為店家設定換罐獎勵面額，第一版只允許：

- 200 元。
- 250 元。

不得用店名文字判斷 200 或 250；必須使用 immutable merchant ID 或明確的 reward catalog 設定。

顧客取得權益時必須 snapshot：

- 面額。
- 適用店家。
- 規則版本。
- 發放時間。
- 到期時間（若產品另有設定）。
- 對應點數扣除紀錄。
- 券號／兌換 ID。

後台日後把 200 改成 250，不得改變已發出的 200 元權益。

### 4.4 同一商業承諾，兩條帳務腿

「給消費者的抵用金」與「給合作店家的換罐補貼」面額相同，但必須分開保存：

1. **消費者權益：** 尚未使用的 200／250 元未來抵用權。
2. **店家補貼：** 顧客實際在該店核銷後，Furmosa 應付店家的 200／250 元。

發券時只建立消費者權益，不立刻建立店家應付。實際核銷成功後才建立 `voucher_fixed_subsidy`：

```text
Furmosa 應付店家 = 券面額
普通寄賣佣金 = 0
```

如此可避免未使用、過期或取消的券提前變成店家應收。

### 4.5 取消與過期

- 自然過期：不退點、不建立店家補貼。
- 尚未核銷取消：依產品核准流程處理，不得留下店家應收。
- 已核銷後取消：只有 HQ 可核准；原補貼不改，另建反向 adjustment，並依正式規則退回點數。
- 同一券號不得同時在兩套來源重複形成補貼。

## 5. 結算公式

每期來源至少分為：

- `consignment_sale`：寄賣成交與已凍結佣金。
- `coupon_subsidy`：換罐／美容券實際核銷補貼。
- `store_collection`：店家代收、但不屬於寄賣成交現金的其他款項。
- `adjustment`：經 HQ 核准的次期更正；現有 runtime 尚未完整支援時不得假裝已支援。

符號：

- `G`：寄賣成交總額。
- `C`：店家寄賣佣金。
- `R`：Furmosa 應付店家的券／換罐補貼。
- `S`：Furmosa 應負擔的其他核准費用。
- `K`：店家代收的其他款項。

```text
店家應付 Furmosa 淨額 = G − C − R − S + K
```

- 結果大於 0：店家付 Furmosa。
- 結果小於 0：Furmosa 付店家。
- 結果等於 0：本期互不付款，但仍保存結算與來源快照。

所有來源先以可稽核精度加總，只在最終新台幣淨額進行一次明確進位。不得逐列任意進位後再加總。

## 6. 結算狀態與鎖定

```text
draft → reviewing → approved → paid
draft／reviewing → cancelled（依既有 allow-list）
```

- 店家只能建立／送出草稿，不能自行核准或標記付款。
- `approved` 後來源、金額、方向與規則版本永久鎖定。
- `paid` 必須有完整付款證據；不能只靠狀態字串。
- 已核准後發現錯誤，只能在次期建立 adjustment。

現有 `SettlementSourceItem`、來源唯一鍵、payload fingerprint 與 rules version 可繼續作為結算快照基礎。

## 7. 實際收付款流水（下一工程階段）

目前只有結算總額與 `paidAt` 不足以支援真實帳務。應建立不可變的 Payment Ledger，每一筆實際金流至少保存：

- 對應結算單。
- 收付方向。
- 金額（整數新台幣）。
- 付款方式。
- 交易／匯款編號。
- 發生時間。
- 建立人與確認人。
- 附件或證明 reference。
- 原付款及其退款／沖銷關聯。
- idempotency key 與建立來源。

結算畫面中的數字必須由流水推導：

```text
已付／已收 = 有效付款流水合計 − 有效退款／沖銷合計
未結清 = 核准淨額絕對值 − 已付／已收
```

狀態規則：

- 尚未支付：`unpaid`。
- 部分支付：`partially_paid`。
- 完全支付：`paid`。
- 超額付款：禁止自動吞掉，必須進待處理差異。
- 退款不刪原付款，建立反向流水。

在 Payment Ledger 完成以前，系統不得聲稱準確支援分期付款、部分付款、尾款、退款與銀行對帳。

## 8. 權限與稽核

| 動作 | 店家 POS | HQ |
|---|---:|---:|
| 查看自己的銷售、佣金與結算來源 | 是 | 是 |
| 修改商品佣金規則 | 否 | 是 |
| 建立／送出結算草稿 | 是 | 是 |
| 核准結算 | 否 | 是 |
| 登記實際付款／收款 | 否 | 是 |
| 新增調整 | 可提出 | 核准後生效 |
| 修改或刪除完成交易 | 否 | 否 |

所有 HQ 規則與付款操作必須記錄 actor、時間、原因與前後值。

## 9. 工程落地順序

### A. 文件與純規則對齊

1. 修正 POS-01 R3 為逐商品／逐店規則。
2. 凍結佣金解析優先順序與 20%／30% 分類。
3. 凍結換罐 200／250 設定、發券與核銷時點。
4. 補齊純函式及邊界測試。

### B. 現有來源稽核

1. 確認每筆寄賣 sale 都有成交額及佣金 snapshot。
2. 確認券補貼只在核銷後形成一次。
3. 找出 Float、缺規則、缺來源鍵與重複鏡像資料。
4. 先做唯讀報告，不自動修正式資料。

### C. Payment Ledger 設計

提出 schema、migration、回復計畫與舊資料處理方案，另行取得使用者同意後才能實作。

### D. HQ／POS 畫面

- 店家：本期銷售、逐筆佣金、換罐補貼、淨額、已付／未付與來源明細。
- HQ：規則設定、結算審核、付款登記、沖銷、差異處理與匯出。

### E. 隔離驗收

先在隔離 PostgreSQL 驗證寄賣銷售、換罐核銷、正負淨額、部分付款、退款、重送與並發；通過後才可規劃 Preview／Production。

## 10. 必測情境

1. 肉乾 300 元、20% → 店家佣金 60、Furmosa 應收 240。
2. 凍乾 300 元、30% → 店家佣金 90、Furmosa 應收 210。
3. 某店某商品個別改為 25%，只影響生效後新交易。
4. 商品無法分類且沒有個別規則 → 阻擋，不猜百分比。
5. 同店 10 點兌換 200；另一店 250；不可跨店累點或使用。
6. 發券但未核銷 → 不產生店家補貼。
7. 核銷 250 元券 → Furmosa 應付店家 250、普通佣金 0。
8. 同一券重送 → 只形成一次補貼。
9. 改後台面額不改歷史券與歷史結算。
10. 結算為正、負、零三種方向。
11. 同一來源並發送出兩張結算 → 只有一張成功鎖定。
12. 部分付款、完全付款、退款與重送均由付款流水正確推導。
13. 已核准結算遇退款 → 原期不變，差額進次期 adjustment。
14. 任一 transaction 中途失敗 → 不留下部分來源、部分付款或部分狀態。

## 11. 尚未決定，不得猜測

下列事項需要另外取得產品／會計決策：

1. 結算週期與到期日。
2. 稅額、發票與扣繳處理。
3. 銀行手續費由誰負擔。
4. 200／250 元權益是否有到期日，以及到期通知規則。
5. 實際付款證明的必要欄位與附件保存期限。
6. 超額付款要退回、保留餘額或抵下期。

這些未決事項不得阻止既有寄賣銷售與換罐履約，但在相應功能實作前必須 fail closed 或維持人工處理。

## 12. 完成定義

只有同時符合下列條件，才可宣稱「店家帳務完整」：

- 本契約與 POS-01／OS Domain Spec 無互相矛盾的現行規則。
- 寄賣佣金、換罐補貼與收款方向都有不可變 snapshot。
- 來源可唯一追溯且不可重複結算。
- 結算核准後不可重開或改寫。
- 真實付款、部分付款、退款與未結清由 Payment Ledger 推導。
- HQ 與 POS 顯示同一套金額與方向。
- 隔離 PostgreSQL 的正常、失敗、重送及並發測試全部通過。
- 未經授權的店家不能查看或操作他店資料。
- 正式 migration、資料修復與部署各自取得明確批准並通過發布閘門。
