## 測試前準備（HQ，不給店員看）

| 項目 | 內容 |
|------|------|
| 對象 | 1 間現有合作美容店（建議：豬窩體系任一間已有換罐寄賣、店員會用 LINE 叫貨的店） |
| 裝置 | 店員自己的手機（Safari / Chrome） |
| 帳號 | 預先建立 `MerchantUser`（見下方指令），現場只給帳密紙本 |
| 商品 | DB 中至少 1 個 `productCategory = JAR_EXCHANGE` 且名稱含店員認得的口味（如雞肉） |
| 環境 | Production 或與 production 資料結構一致的 staging；Phase 1＋2 migration 已套用 |
| 觀察員 | 1 人；計時、點擊、卡住處；不提示操作路徑 |

### 建立店員帳號

```bash
MERCHANT_ID=<Merchant.cuid>
USERNAME=<店家好記的帳號>
PASSWORD=<臨時密碼>
DISPLAY_NAME=<店員顯示名>
npm run merchant:create-user
```

必要環境變數（依部署）：`DATABASE_URL`、既有 Next Auth／App URL。店員端只需知道 POS 網址（例如 `https://…/pos/login`）。

1. 哪一步最難懂？

## HQ 同步檢查清單（測試日當天）

1. Merchant 送「我要自己選」→ HQ 改數量 → 填預計到貨日 → 核准  
2. 確認建立既有 `merchant_restock` Shipment、`shipmentId` 寫回、`approvedSnapshot` 有值  
3. Merchant 看到狀態與到貨日  
4. 再點一次核准 → 不新增第二張 Shipment  
5. 再測「請幫我配」→ HQ 新增品項 → 核准建 Shipment  
6. RestockRequest **不**扣門市庫存；庫存仍走 Shipment shipped／delivered
