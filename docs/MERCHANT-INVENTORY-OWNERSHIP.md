# 店家庫存批次與買斷月結排除

## 行為

- 商品主檔與店家預設合作方式不變。`MerchantStockLot` 按店家、商品規格保存批次所有權、來源、贊助標記與餘量。
- HQ/POS 均先在同一交易中更新庫存再建立流水。資料庫 trigger 以明確規格與鎖定庫存核對批次合計，FIFO 扣批次，保存不可改寫的 `inventoryAllocation`。
- 買斷售出仍保留完整成交單價、數量與營業額；`settlementQuantity=0`，佣金／公司寄賣應收為零。混合批次只認列寄賣部分。
- 新舊月結入口都排除零認列數量；舊交易的 NULL 快照保持原行為。純盤點不再推算成交價。
- 已分批庫存新增須走有來源訂單的收貨流程，不猜測盤盈屬於買斷或寄賣。
- 撤銷未結算動作還原原批次，已結算動作不可撤銷；已入庫的批次來源需用退回處理，不能刪除來源。

## 發布與特定資料修正

1. 此 PR 使用 `standard` plan，只執行新增結構及 trigger，不回填其他店家。
2. 通過 CI（包含隔離 Postgres 與桌機／手機 POS 驗收）後，透過 Deploy Production 鎖定 PR 與完整 head SHA。
3. 核對 Railway 相同 merge SHA 與正式 origin readiness。
4. 執行 `node scripts/ops/reconcile-manlisa-buyout.mjs` dry-run，核對曼莉莎實際庫存20包，15包零元贊助、5包原價格參考值，沒有中途銷售或既存批次。
5. 已授權資料修正使用相同腳本 `--apply`，Serializable 交易內拆分買斷訂單並建立15/5兩筆批次，不新增、不重扣實物庫存；原單快照保存在 audit。
6. 5包的原參考價165不是已驗證的買斷價格。新買斷訂單標記未付款，備註價格／收款待核實，禁止推定已付款；原贊助單運費及付款狀態保留。
7. 回查20包實體量、批次量20、贊助15、買斷5及10月應收228；執行唯讀正式 smoke。不得在正式環境建立測試銷售。

## 驗收

隔離 PostgreSQL 相容引擎實際執行同一 migration，驗證買斷20售1剩19且寄賣應收0、混合FIFO僅認列寄賣數量、歷史NULL快照、盤點零元、規格遺漏／批次失衡完整 rollback、收貨重送及撤銷還原。

## 回復

新增結構不刪除既有資料。發布失敗時停在前一版流量；資料修正前可回復前版程式。資料修正後若須回復，先停止該店寫入，依 audit 與已產生批次流水逐筆反向處理；不可直接切回不識別所有權的舊版收銀，也不可刪除批次／快照。新舊欄位均保留供稽核。
