# Shopify → HQ 商品自動化工作包

## 固定資料責任
- Shopify：顧客品名、照片、介紹、規格識別、官網售價、顧客產品資訊。
- HQ：供應商、成本、批發及寄賣約定價、分潤、倉庫與庫存流水。
- 店家 POS：只顯示有權販售且有該店可售庫存的規格。
- 商品同步不得更新歷史 Order / OrderItem / Shipment 或 InventoryTransaction。
- 官網庫存回寫需扣除保留數量並防止 Shopify 接單與 HQ 出貨重複扣帳。

## 第一工作包（本 PR）
- 擴充現有商品來源，讀取主圖、純文字介紹、productType 與既有產品資訊欄位。
- 在既有商品檢查畫面列出上架必填資料缺漏，使用固定錯誤 code / field / rulesVersion。
- 已綁定商品使用 variant ID 優先；來源缺失時停止，不以舊 SKU 偷換綁定。
- 唯一對應商品可同步主圖與介紹。成本、庫存、商務條件與訂單不在寫入範圍。
- 欄位完整僅代表格式完整，不代表原廠查驗完成，也不等於自動建檔資格。
- 保留既有人工同步入口；本工作包尚未啟用背景同步或自動發布。

## 後續工作包（尚未啟用）
1. 以固定 metadata 記錄類型、販售單位、淨重、包裝數、配送溫層和通路設定；先核對全店既有定義。
2. Draft 先同步 HQ 草稿；通過完整規則後建立 HQ 商品及所有規格，缺少成本不得猜填零。
3. 商品事件先持久化再處理，使用 shop + product / variant ID、來源版本與 payload hash 去重。
4. 背景工作需有領取鎖、逾時回收、有限重試、最後成功時間與差異報告；定期對帳補漏。
5. 下架只停用對應通路，不刪除庫存歷史；不得因一次讀取缺失封存其他通路專用規格。
6. 用品與食品由不同模板讀取 metadata；統一 CSS 不存放於每款商品描述。
7. 商品連線完成與 POS 販售資格分開呈現，服務及組合走專屬履約／組成檢查。

## 驗收矩陣
|案例|預期|
|食品／用品|只要求對應類型欄位，不互相填餵食或材質|
|類型未知|列出待處理，不以品名猜類型|
|SKU 空白／重複|具體列出規格，停止自動對應|
|改 SKU|保留既有變體 ID 對應|
|變體消失|停止並提示，不連到其他商品|
|更新圖文|只更新商品欄位，庫存、成本及歷史訂單不變|
|服務／組合|未完成履約／組成規則前不自動建立|
|來源讀取失敗|不套用不完整商品清單|

正式發布前須在隔離 Preview 完成驗收；本工作包沒有 migration、backfill 或正式資料修復。

## 第二工作包：有條件的自動草稿建檔（預設關閉）

- `POST /api/cron/shopify-catalog` 使用既有 Cron Bearer 驗證。
- `SHOPIFY_CATALOG_AUTOMATION_ENABLED=true` 才執行；預設無排程、無背景執行。
- `SHOPIFY_CATALOG_AUTOMATION_MODE=inspect` 只預覽；明確設為 `create` 才處理，每次最多兩個規格。
- 沿用既有候選建檔的交易鎖、序列化交易、CAS 與稽核紀錄，只建立 HQ 草稿，不自動入庫或發布。
- 每件用品現在可使用規格單位「件」。重量模式只能使用明確淨重，不能拿 Shopify 出貨重量代填。
- 新增規格須確認父商品關係；既有同名 HQ 商品未綁定時留人工處理，不以名稱自動認領。
- 適用「新商品草稿建檔」，現有商品更新仍使用第一工作包既有同步入口。

自動建檔使用待設定的私有 Shopify JSON metafield `custom.hq_catalog_profile`，本次沒有建立正式定義或寫入商品。此欄位含成本，必須保持 Admin-only，禁止開放 Storefront 存取或印在商品描述。

```json
{"version":1,"autoCreate":true,"category":"accessories","variants":{"65165705740665":{"mode":"unit","unit":"件","unitQty":1,"cost":300}}}
```

`autoCreate` 是營運人員的明確設定，不等同原廠查驗證據。全部變體都要填完整規格；SKU、圖文、類型專屬資料缺漏時不會自動建立。服務與組合仍須完成各自履約規則。

此入口尚需隔離資料庫端到端驗收、設定私有欄位與排程後才能啟用；不得把程式已存在回報為正式自動化已啟用。
