# OMS 第三階段：審核與內部出貨單

此版本尚未部署；不是完整 OMS 驗收完成。累積於第二階段收單版本。

## 本階段完成的程式

- 訂單詳情沿用既有外觀，新增商品對應、商品及配送溫層、收件及 7-11 門市資料表單。
- 「儲存並檢查」進 REVIEW；「確認訂單」進 READY 並記錄 HQ 審核者與時間。
- 「建立 HQ 出貨單」是另一個明確動作，只能在 READY 後建立既有 Shipment，進 FULFILLMENT_PENDING。
- 此 Shipment 是內部待出貨單，沒有呼叫黑貓、7-11 或任何物流供應商，也沒有 Shopify fulfillment 回寫。
- 審核草稿存在既有 StatusAuditLog.metadataJson，綁定來源快照 SHA-256。未再新增 schema/migration。
- 審核動作重新讀取 HQ 使用者角色，只准 admin/staff；不使用 POS session，不更動認證程式。
- 審核與 webhook 使用相同訂單鎖。來源更新、版本衝突、未儲存的表單、取消或已進出貨流程都不能跳過檢查。
- 建立出貨前再次檢查庫存；同筆出貨使用唯一、固定編號及訂單鎖防重送。
- 金額與數量只讀 Shopify 快照；不接受瀏覽器金額，也不修改客戶共用資料。
- 訂單列表依檢查結果顯示綠色、黃色、紅色，而非固定「待檢查」。

## 檢查與限制

- 付款未全額 paid、退款、取消、來源版本缺失、非 TWD、無效金額/數量皆阻擋。
- 未對應或停用商品阻擋；缺 SKU 可人工選取有效商品，保留黃色提醒。
- 庫存採 InventoryBalance 合計扣除 pending/packed ShipmentItem，合併同商品多行需求。沒有庫存資料或不足會阻擋。
- 新 OMS 出貨使用共用庫存鎖，但舊出貨流程不使用此鎖。這不是全系統庫存保留保證；物流正式放行仍需完整倉庫/規格配置及最終庫存檢查。
- Product 沒有可靠溫層欄位，由審核人員確認，不以商品名稱猜測。不同商品溫層或配送溫層衝突時阻擋，尚無自動拆單。
- 多規格商品（priceTiers 非空）、特殊商品及非實體訂單先保留 HQ、阻擋一般出貨，待補規格/特殊履約路徑。這表示部分 CK-08 等商品仍不能通過出貨審核，並非完整商品相容性已完成。
- 配送僅本版黑貓宅配 / 7-11；7-11 要六位數店號、名稱及地址。不宣稱已驗證門市在物流供應商端有效。
- 贈品核對是人工勾選，尚未串促銷引擎自動補贈品。
- 相同聯絡欄位、相同總額且下單時間前後一天有另一筆同店訂單時提示重複，允許人員核對後確認。不是地址/電話正規化或跨店完整防詐系統。
- 當事人修改快照以外的審核資料，不會回寫 Shopify。
- 仍未接自動完整檢查工作佇列；收單先 NEW，人工儲存時執行完整檢查。
- 舊 Shipment 狀態操作仍對 OMS 阻擋，避免繞過新流程。尚未完成 OMS 待出貨→已出貨路徑。

## 驗證

- Shopify 與 orders 目錄相關測試 56 項通過，包含 9 項新增審核檢查/交易契約測試。
- 交易測試使用 in-memory double，未執行真正 PostgreSQL 鎖、rollback 或並發庫存測試。
- TypeScript 全專案檢查仍有 25 個既存錯誤；與未修改基線相同，新增檔案未引入錯誤。
- 未 build、未執行 migration、未 backfill、未寫正式資料、未 push/merge、未部署 Preview/Production。
- 尚未實際瀏覽器 UI 驗收。
