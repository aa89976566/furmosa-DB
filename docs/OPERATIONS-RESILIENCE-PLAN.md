# 匠寵營運不中斷計畫

更新日期：2026-09-25

## 原則

匠寵需要的是小團隊可維護的營運助手，不是大型 ERP。每一條流程都依下列順序設計：

1. 先安全保存人員已輸入的資料。
2. 正常案件能自動走到下一步。
3. 單一案件失敗時，只隔離該案件，不阻塞其他工作。
4. 可安全重試，而且重複操作不會重複扣庫存、加點或核銷。
5. 需要人工處理的例外集中在 HQ「任務」，並清楚顯示下一步。

## 今日完成清單

### P0：HQ 新增訂單不中斷

- [x] 確認訂單與待出貨資料在同一個資料庫交易中建立。
- [x] 確認訂單完成後的快取與通知失敗，不會回頭讓已建立的訂單顯示失敗。
- [x] 新增訂單表單自動暫存於操作人員的瀏覽器。
- [x] 重新整理後恢復客戶、商品、物流、付款與備註。
- [x] 伺服器送出失敗時保留畫面與草稿，讓人員修正後重試。
- [x] 訂單成功建立後才清除草稿。
- [x] 草稿依 HQ 使用者與「新增／複製訂單」分開，24 小時後自動失效。
- [x] 草稿格式、有效期與損壞資料已有自動測試。

### 今日驗收方式

1. 登入 HQ，進入「新增訂單」。
2. 選客戶、加入商品並填寫物流資料。
3. 重新整理頁面，確認資料自動恢復，畫面顯示「已恢復」。
4. 刻意留下缺少資料並送出，確認錯誤只停留在本張表單，其他訂單仍可操作。
5. 補齊資料後建立訂單，確認只產生一張訂單及一筆待出貨資料。
6. 回到新增訂單頁，確認已成功建立的舊草稿不再出現。

## 現況盤點與阻塞矩陣

以下結論以 2026-09-25 最新 `main` 程式碼為準；「已有」代表目前有後端保護，不只是在畫面上顯示錯誤。

| 流程 | 現有保護 | 目前缺口 | 優先級與下一步 |
| --- | --- | --- | --- |
| HQ 人工建立訂單 | 訂單與待出貨在同一個資料庫交易建立；建立後通知失敗不回滾訂單 | 原本重新整理或送出失敗後沒有草稿恢復 | **P0，本次完成**：瀏覽器自動暫存、恢復、成功後清除 |
| Shopify 訂單 | Webhook 事件有唯一鍵、原始快照、狀態與嘗試次數；相同事件不重複建單 | `FAILED` 事件目前沒有背景工作依 `nextAttemptAt` 自動重跑，也沒有進入 HQ 任務頁 | **P0 下一項**：建立有上限的重試工作；最終失敗建立一筆異常任務 |
| POS 一般銷售／入庫 | 既有流程可留下庫存交易紀錄 | 尚未用同一個操作識別碼證明「連點三次只寫一次」；錯誤分散在各頁 | **P0**：為收銀與入庫加入操作鍵、唯一限制及重送原結果 |
| LINE 輸入舊序號 | 序號狀態變更、會員服務、點數與營收紀錄在同一交易；序號用條件更新防止重複使用 | 點數帳本只有一般索引，沒有來源唯一限制；非序號型加點仍可能重複寫入 | **P0**：為點數來源增加唯一性，所有加點都用來源鍵安全重送 |
| POS 完成換罐 | 換罐完成、舊罐歸還、新罐發出與加點在交易中；完成狀態可重送；LINE 通知失敗不回滾完成結果 | 通知失敗只寫伺服器紀錄，執行人員在 HQ 看不到、也無法重送 | **P1**：失敗通知建立異常任務，提供重送按鈕 |
| LINE 兌換十點獎勵 | 兌券、扣點與成本紀錄在同一交易 | 同一會員同時點兩次時沒有會員鎖或請求唯一鍵；流水號用「查最後一筆再加一」也可能衝突 | **P0**：會員鎖＋兌換請求鍵；流水號碰撞可重試 |
| 店家核銷折價券 | 先驗證店家、狀態與期限，再留下核銷店家與人員 | 驗證和更新分成兩次操作；兩台 POS 同時核銷時，缺少 `status=available` 的條件更新 | **P0**：改成單一條件更新；失敗回傳已核銷的時間與店家 |
| HQ 任務頁 | 已有負責人、優先級、狀態、期限與關聯編號 | 尚未成為 Shopify、LINE、物流、換罐的共用錯誤出口，缺少重試資訊 | **P1**：先不擴充成大型工單；補錯誤代碼、來源、重試狀態與動作即可 |

### 盤點後的判斷

- 最成熟的是 Shopify 事件收件與 POS 換罐完成交易；主要缺口是「失敗後誰來重試、員工去哪裡看」。
- 最高風險不是資料完全沒交易，而是獎勵兌換、折價券核銷與一般 POS 寫入缺少完整防重複證據。
- 任務頁不需要重做；先讓失敗流程自動建立或更新同一筆任務，避免一個故障變成大量重複待辦。
- 本次先解決 HQ 建單資料遺失，因為它直接中斷人工營運，且不需要資料庫遷移即可安全交付。

## 下一階段工作順序

### P0：所有寫入都能安全重試

依序處理 Shopify 訂單、POS 入庫、換罐序號、點數、折價券與核銷。每個動作都必須有唯一識別碼；相同請求重送時回傳原結果，不得重複寫入。

驗收：同一動作連點或重送三次，訂單、庫存、點數與核銷都只發生一次。

### P1：任務頁升級為異常處理中心

共用欄位：問題類型、來源系統、關聯資料、目前原因、建議下一步、重試次數、負責人、最後發生時間、完成時間。先接 Shopify 同步失敗與 LINE 通知失敗，再接物流、換罐及庫存差異。

驗收：人員不用問工程師，就能在任務頁找到失敗案件、看懂原因並安全重試。

### P1：換罐與折價券完整接力

序號登記成功後，以後端單一交易完成序號使用、店家庫存扣除與客戶加點；集滿十點建立折價券；POS 核銷後回寫 HQ。LINE 僅負責顯示與通知，不是點數或券的最終答案。

驗收：任一步驟失敗只留下待辦；重新執行不重複扣庫存、加點或核銷。

### P2：首頁顯示今日待處理

只顯示待出貨、待收款、待驗收入庫、換罐異常、庫存不足與同步失敗；數字可直接進入已篩選的工作清單。

驗收：執行人員登入後，可以在一個畫面判斷今天先處理什麼。

### P2：每日自動核對

每日核對訂單、付款、庫存、換罐點數與折價券核銷，僅對差異建立任務，不寄送大量正常報表。

驗收：沒有差異時保持安靜；有差異時每一筆都有來源與建議處理方式。

## 上線規則

- 每次只上線一條可完整驗收的流程。
- 合併前執行相關自動測試與人工驗收。
- 正式站確認成功前，不修改真實庫存、序號或客戶點數。
- 部署失敗時保留上一個可用版本；回復版本不得依賴臨時修改正式資料。
