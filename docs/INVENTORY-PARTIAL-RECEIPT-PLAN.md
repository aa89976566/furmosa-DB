# WP2a 分批收貨變更方案（已授權開發及隔離驗證）

## 範圍

沿用現有進貨單、入庫單與庫存交易，不建立另一套庫存。此工作包只處理目前已支援的 g 與已知成本；多單位、成本待補及日期待補另行實作，不假稱完成。

員工從原進貨單填「本次實收」，看到訂購、已收、剩餘，按一次確認。未到貨項目填 0 或空白不入庫。收完才結案；尚有剩餘時仍留在待收貨清單。禁止超收、負數、小數、全空及重複商品行。

## 已確認障礙

- PurchaseReceipt.purchaseOrderId 為唯一欄位，PurchaseOrder.receipt 是單筆關聯。
- receivePurchaseOrder 會先將整單標為 received，再按訂購總量入庫。
- 庫存交易 eventKey 使用進貨單加來源行，同一行第二次收貨會衝突。
- 供應商單號在入庫單也有唯一限制，分批不能每次複製原進貨單號。
- 運費等共同成本目前整單一次分攤；分批不能重複全額計入。

## 建議資料結構：新增相容關聯

保留既有 purchaseOrderId 唯一關聯與舊 receipt 欄位，不刪除或改寫歷史。

1. PurchaseReceipt 新增可空的來源進貨單關聯欄位（多對一）、唯一提交識別碼及提交內容雜湊；PurchaseOrder 新增對應收貨集合。新流程只寫新的多次收貨關聯；讀取時以 ID 去重合併舊關聯與新關聯。
2. PurchaseReceiptItem 新增可空的來源進貨單行關聯及查詢索引，供本次與累計實收追溯。舊單不回填；舊單據依原關聯及商品 ID 讀取既有已收量，因現有訂購行已有單內商品唯一限制，不以名稱猜測。
3. 新增提交欄位均允許歷史為空；外鍵禁止刪除來源單，金額繼續使用 Decimal 與整數分運算，不引入 Float 金額。
4. 不執行正式 migration、seed、資料回填或庫存更動；先在隔離資料庫驗證 migration 與新舊單查詢。

## 收貨交易規則

- 伺服器驗證倉庫權限、來源單狀態、行歸屬與非空提交識別碼；相同識別碼不同內容必須拒絕。
- Serializable 交易中鎖定來源單，先檢查既有提交，再讀取合併後已收量；本次不得超過剩餘量。衝突有限重試，重試仍使用同一識別碼。
- 每次收貨各有入庫單；庫存交易識別使用收貨批次與來源行。建單、明細、庫存加量、成本更新與單據狀態必須在同一交易提交。
- 重送回傳原入庫單，不再加庫存；同時收貨不得突破訂購量。
- 原供應商單號留在來源進貨單；新入庫單透過來源關聯顯示，不複製到有唯一限制的入庫單號欄位。每批附加單據的填寫方式須清楚區別供應商發票與原進貨單號。
- 進貨單總價與各項共同成本按已收比例計算累計應分攤分數，本次取累計差額；最後一批承接尾差。不得每批重複計入整單運費、稅額或折扣。各成本分量與每行原料金額分別對帳，合計必須等於原單；不允許分攤後負成本。
- 入庫明細保留實際成本快照；最後一批才設定 received、receivedAt 與 receivedById。部分收貨維持 pending_receipt，畫面另顯示部分到貨，不新增任意狀態值。
- 頁面更新失敗不回報交易失敗；連線結果不明時以原提交識別碼查詢或重試。

## 影響檔案

- prisma/schema.prisma 與單一新增式 migration。
- lib/inventory/purchase-orders.ts、post-purchase-receipt.ts：來源關聯、累收、去重與成本分攤。
- 現有進貨單明細與確認 action：實收輸入、提交識別、剩餘量與批次紀錄。
- 進貨清單、入庫明細：相容新舊來源連結與部分收貨提示。
- 相關單元測試及隔離 PostgreSQL 整合測試。
- 不修改 HQ/POS 登入、出貨扣庫觸發器或 POS 扣庫服務。

## 驗收矩陣

| 情境 | 必須結果 |
| --- | --- |
| 訂購 1,000g，先收 400g | HQ 僅加 400g；剩餘 600g；原單仍待收 |
| 再收 600g | 累收 1,000g；原單結案；兩筆入庫可追溯 |
| 第二批提交重送 | 返回同一筆入庫；庫存與成本不再變動 |
| 相同識別碼改數量 | 拒絕，不寫入 |
| 兩人同時收剩餘量 | 最多成功一份足額收貨，另一份重新核對 |
| 超收、外單行、無權限、作廢單 | 伺服器拒絕且整筆無變動 |
| 0、空白與混合行 | 只入庫正數行；全空不可確認 |
| 成本尾差與多行分批 | 各行與共同成本最終精確對回原單，不重複分攤 |
| 既有已收／未收單 | 原歷史可查，舊已收單不可再次收貨 |
| 任一中途寫入失敗 | 單據、庫存與成本整筆回復 |
| 出貨／盤點同時更新 | 交易衝突不覆蓋其他庫存異動 |

## 發布與回復

1. 核准本方案後才修改 schema；僅新增可空欄位、索引與外鍵，不刪除舊欄位、不回填資料。
2. 隔離 PostgreSQL migration 與交易整合測試、CI、Preview 驗收全部通過後，使用受控 Deploy Production exact PR/SHA 與 standard migration plan。
3. migration 已執行但尚無新收貨時，可回復舊應用並保留新增欄位，禁止 down migration 刪資料。
4. 一旦出現新分批收貨，舊應用不理解新關聯，可能誤認整單未收；不能直接回復舊版本。應停用收貨寫入入口，保留讀取與資料，以具新舊讀取相容能力的修正版回復服務。
5. 不以刪除入庫單或反向改庫存作回復。正式 smoke 只讀，不建立示範進貨單。

本方案完成不表示功能已實作或正式資料已遷移。
